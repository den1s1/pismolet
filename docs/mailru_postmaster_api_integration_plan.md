# План внедрения интеграции Mail.ru Postmaster API

Статус: утверждён к реализации  
Дата фиксации: 2026-07-09  
Контур: production  
Ответственное направление: техническое

## 1. Статус проекта

Письмолёт работает в production. Все этапы ниже являются развитием действующей системы и должны выполняться с обратной совместимостью, безопасными миграциями, наблюдаемостью и возможностью отката.

Термин `MVP` не используется для планирования текущих и будущих технических работ. Старые документы и имена файлов с этим термином считаются историческими и не определяют текущий статус продукта.

## 2. Текущее состояние

На момент фиксации плана уже выполнено:

- домен `pismolet.ru` добавлен и подтверждён в Mail.ru Postmaster;
- SPF, DKIM и DMARC проходят проверку;
- FBL настроен;
- в исходящие письма добавлен заголовок `X-Postmaster-Msgtype`;
- значение `X-Postmaster-Msgtype` строится из идентификатора рассылки, содержит только латинские буквы и цифры и ограничено 32 символами;
- статистика Mail.ru Postmaster просматривается вручную;
- обнаружен практический сигнал: при росте объёма значительная доля писем может попадать в категорию «Возможно спам», поэтому автоматизированное наблюдение требуется как часть production-эксплуатации.

## 3. Цели интеграции

Интеграция должна:

1. Автоматически получать статистику Mail.ru Postmaster по домену `pismolet.ru`.
2. Хранить ежедневную историю показателей в собственной БД.
3. Получать статистику по отдельным рассылкам через `msgtype`.
4. Показывать данные в административной панели.
5. Выявлять ухудшение доставляемости, рост жалоб и проблемы SPF, DKIM, DMARC.
6. Формировать операционные предупреждения без влияния на отправку при недоступности внешнего API.
7. Создать основу для последующего использования репутационных данных в антиспам-правилах и управлении скоростью отправки.

## 4. Не входит в первый production-релиз интеграции

На первом этапе не реализуются:

- автоматическая остановка всех рассылок только по одному значению из Postmaster;
- автоматическая блокировка клиента без ручной проверки;
- показ агрегированных данных Mail.ru клиентам;
- замена внутренних метрик доставки данными Mail.ru;
- получение адресов пожаловавшихся пользователей через API — для этого используется отдельно настроенный FBL.

## 5. Источники данных Mail.ru Postmaster

Используются официальные методы:

- `/ext-api/reg-list/` — список подтверждённых доменов;
- `/ext-api/troubles-list/` — проблемы SPF, DKIM и DMARC;
- `/ext-api/stat-list/` — суммарная статистика за период;
- `/ext-api/stat-list-detailed/` — ежедневная статистика за период;
- параметры `domain=pismolet.ru` и `msgtype=<идентификатор рассылки>` — статистика конкретной рассылки.

Статистика Mail.ru привязывается к домену из DKIM-подписи `d=`, поэтому основным доменом интеграции является `pismolet.ru`.

## 6. Архитектура

### 6.1. Конфигурация

Добавить настройки:

```text
MailruPostmaster__Enabled=true
MailruPostmaster__Domain=pismolet.ru
MailruPostmaster__RefreshToken=<secret>
MailruPostmaster__SyncHourMoscow=6
MailruPostmaster__BackfillDays=30
MailruPostmaster__ResyncRecentDays=3
MailruPostmaster__RequestTimeoutSeconds=15
```

Правила:

- `RefreshToken` хранится только в production-секрете или `EnvironmentFile` systemd;
- токен запрещено добавлять в репозиторий, логи, audit trail и HTML;
- `Enabled=false` полностью отключает фоновые запросы без влияния на отправку писем;
- URL OAuth и Postmaster API должны иметь безопасные значения по умолчанию, но оставаться переопределяемыми для тестов.

### 6.2. Клиент OAuth

Добавить `IMailruPostmasterTokenProvider`.

Обязанности:

- получать `access_token` через `refresh_token`;
- хранить `access_token` только в памяти;
- учитывать срок жизни токена и обновлять его заранее;
- при первом `403` принудительно обновить токен и повторить запрос один раз;
- не логировать токены и полный ответ OAuth;
- защищать обновление токена от параллельных запросов.

### 6.3. Клиент Postmaster API

Добавить `IMailruPostmasterClient` с типизированными методами:

```csharp
Task<RegisteredDomainsResult> GetRegisteredDomainsAsync(...);
Task<TroublesResult> GetTroublesAsync(...);
Task<DomainStatisticsResult> GetStatisticsAsync(...);
Task<DomainDailyStatisticsResult> GetDetailedStatisticsAsync(...);
```

Требования:

- `HttpClientFactory`;
- таймаут;
- корректная обработка `403`, `429`, `5xx`, сетевых ошибок и невалидного JSON;
- повтор запроса после `429` с учётом ответа API;
- ограничение частоты запросов ниже лимита Mail.ru;
- логирование только безопасных полей: endpoint, domain, date range, msgtype, status code, duration;
- недоступность Mail.ru не должна блокировать отправку писем, модерацию, оплату или работу кабинета.

### 6.4. Хранилище

Добавить таблицы или эквивалентные сущности.

Поля:

- `Code`;

- `LastSeenAt`;

Поля:

- `LastAttemptAt`;

Правила хранения:

- запись метрик выполняется через идемпотентный upsert;
- повторная синхронизация последних дней обновляет существующие строки;
- исходные токены и персональные данные получателей не сохраняются;
- полный сырой JSON по умолчанию не хранится;
- при необходимости диагностики допускается хранить только хеш ответа и безопасный технический фрагмент.

## 7. Фоновая синхронизация

Добавить `MailruPostmasterSyncHostedService`.

### 7.1. Ежедневный цикл

Один раз в сутки по московскому времени:

1. Проверить, что интеграция включена.
2. Получить список зарегистрированных доменов.
3. Убедиться, что `pismolet.ru` присутствует в списке.
4. Получить `troubles-list`.
5. Получить детальную статистику домена за последние `ResyncRecentDays`.
6. Обновить ежедневные метрики через upsert.
7. Синхронизировать статистику завершённых рассылок по `msgtype`.
8. Обновить состояние синхронизации.
9. Сформировать предупреждения при ухудшении показателей.

### 7.2. Первичный backfill

При первом включении:

- загрузить доменную статистику за последние 30 дней;
- не пытаться получать статистику конкретных рассылок за периоды до появления корректного `X-Postmaster-Msgtype`;
- выполнять backfill порциями и соблюдать лимиты API;
- повторный запуск не должен создавать дубли.

### 7.3. Синхронизация по рассылкам

В очередь синхронизации попадают рассылки:

- со статусом `Sent`, `Sending`, `Failed` или завершённой модерацией после начала отправки;
- имеющие хотя бы одного адресата доменов Mail.ru/VK Mail, если такая классификация доступна;
- отправленные после включения корректного `X-Postmaster-Msgtype`.

Алгоритм:

1. Для каждой подходящей рассылки использовать тот же `msgtype`, который добавляется в SMTP-заголовок.
2. Первый запрос выполнять не ранее следующего дня после отправки.
3. Повторять запрос несколько дней, так как статистика может уточняться.
4. После стабилизации данных снизить частоту повторов.
5. Ограничить число запросов за один цикл и переносить остаток очереди на следующий запуск.

Для малых объёмов рядом с процентами показывать абсолютные значения и предупреждение о низкой выборке.

### 8.2. Карточка рассылки

Добавить блок `Mail.ru Postmaster` в профиль рассылки администратора.

Показывать:

- `msgtype`;
- период статистики;
- количество писем Mail.ru по внутренним данным;
- `messages_sent` по данным Postmaster;
- доставлено;
- возможно спам;
- точно спам;
- жалобы;
- прочитано;

Не смешивать показатели Mail.ru с общими показателями всей рассылки. В интерфейсе должно быть явно указано, что это статистика только экосистемы Mail.ru.

### 8.3. Ручные операции

Для администратора добавить:

- `Синхронизировать сейчас`;
- `Повторить ошибочную синхронизацию`;
- просмотр журнала последних запусков;
- включение и отключение интеграции через конфигурацию, а не через публичный UI.

Ручной запуск должен иметь защиту от параллельных синхронизаций и ограничение частоты.

## 9. Предупреждения и эксплуатационные сигналы

Вводить предупреждения в два шага.

### 9.1. Режим наблюдения

Первые 14 дней после включения API:

- собирать данные;
- показывать сигналы только в админке;
- не влиять автоматически на скорость отправки и модерацию;
- определить нормальный диапазон показателей для текущего объёма Письмолёта.

### 9.2. Рабочие предупреждения

После накопления базовой истории:

- проблема SPF, DKIM или DMARC с отрицательным кодом — критическое предупреждение;
- появление `spam > 0` — критическое предупреждение;
- появление жалоб — предупреждение с указанием абсолютного количества и доли;
- резкий рост `probably_spam_percent` — предупреждение;
- отсутствие успешной синхронизации более 48 часов — техническое предупреждение;
- несколько последовательных ошибок API — предупреждение дежурному администратору.

Пороговые значения должны храниться в конфигурации и учитывать минимальный объём выборки. Проценты без абсолютных значений использовать нельзя.

## 10. Влияние на отправку

Принцип: интеграция Postmaster является наблюдаемостью, а не критической зависимостью отправки.

Правила:

- отказ Mail.ru API не останавливает отправку;
- ошибки OAuth не влияют на пользовательский сценарий;
- синхронизация выполняется вне транзакций отправки;
- автоматическое снижение скорости или остановка допускаются только отдельным решением после накопления статистики;
- перед включением автоматического влияния обязательны ручное подтверждение правил, аварийное отключение и журнал причин решения.

## 11. Безопасность

Обязательно:

- `refresh_token` хранить вне репозитория;
- права файла с секретом — только для пользователя сервиса;
- не выводить токены в `journalctl`;
- не добавлять токены в исключения, тексты ошибок и дампы HTTP;
- маскировать заголовки авторизации;
- ограничить исходящие запросы только официальными доменами Mail.ru;
- использовать HTTPS;
- выполнять ротацию `refresh_token` при подозрении на утечку;
- документировать процедуру ротации и восстановления интеграции.

## 12. Наблюдаемость самой интеграции

Добавить метрики и структурированные логи:

- `mailru_postmaster_sync_started`;
- `mailru_postmaster_sync_completed`;
- `mailru_postmaster_sync_failed`;
- `mailru_postmaster_token_refreshed` без значения токена;
- `mailru_postmaster_rate_limited`;
- `mailru_postmaster_domain_metrics_upserted`;
- `mailru_postmaster_mailing_metrics_upserted`;
- длительность синхронизации;
- количество обработанных дней;
- количество обработанных рассылок;
- количество активных проблем.

В логах не должно быть адресов получателей.

## 13. Тестирование

### 13.1. Unit-тесты

Проверить:

- разбор успешных ответов всех методов;
- пустые ответы;
- `ok=false`;
- невалидный JSON;
- обновление access token;
- повтор после `403`;
- обработку `429`;
- идемпотентный upsert;
- расчёт предупреждений;
- нормализацию `msgtype`;
- отсутствие токенов в логах.

### 13.2. Интеграционные тесты

Через подменяемый `HttpMessageHandler` проверить:

- полный цикл OAuth → API → БД;
- повторную синхронизацию того же периода;
- обновление уже существующих метрик;
- частичный сбой одного endpoint;
- продолжение работы после сетевой ошибки;
- соблюдение лимита запросов;
- корректное восстановление после перезапуска приложения.

### 13.3. UI-тесты

Проверить:

- страницу доменной статистики;
- отображение активных проблем;
- отсутствие данных;
- малую выборку;
- карточку конкретной рассылки;
- ручной запуск синхронизации;
- недоступность раздела неадминистратору.

### 13.4. Production smoke-test

После выкладки:

1. Включить интеграцию.
2. Убедиться, что домен найден в `reg-list`.
3. Получить `troubles-list`.
4. Загрузить доменную статистику за один день.
5. Сверить показатели с веб-интерфейсом Postmaster.
6. Отправить тестовую рассылку на Mail.ru с новым `msgtype`.
7. На следующий день сверить статистику конкретной рассылки.
8. Проверить отсутствие токенов в логах.
9. Проверить, что временная недоступность API не влияет на отправку.

## 15. Критерии готовности

Интеграция считается введённой в production, когда:

- секреты настроены вне репозитория;
- домен автоматически определяется как подтверждённый;
- ежедневная синхронизация работает не менее 7 дней без потери данных;
- повторный запуск не создаёт дубли;
- активные проблемы SPF, DKIM и DMARC отображаются в админке;
- доменные метрики сверены с веб-интерфейсом Mail.ru;
- статистика хотя бы одной реальной рассылки получена по `msgtype`;
- ошибки API не влияют на отправку писем;
- есть дата последней успешной синхронизации и понятное состояние ошибки;
- тесты зелёные;
- выполнен production smoke-test;
- описаны процедуры ротации токена и отключения интеграции.

## 16. Откат

Откат должен выполняться без удаления накопленных данных.

Порядок:

1. Установить `MailruPostmaster__Enabled=false`.
2. Перезапустить сервис.
3. Убедиться, что фоновые запросы прекратились.
4. Не откатывать SMTP-заголовок `X-Postmaster-Msgtype`, так как он не влияет на доставку и нужен для последующей статистики.
5. Не удалять таблицы метрик при обычном откате приложения.
6. При проблемах с токеном выполнить его ротацию без изменения схемы БД.

## 17. Синхронизация с другими документами

На текущем этапе изменение относится к технической эксплуатации и фиксируется в этом документе.

Синхронизация `docs/specification.md` потребуется, если данные Postmaster начнут:

- показываться клиентам;
- автоматически влиять на модерацию;
- автоматически ограничивать отправку;
- использоваться в публичных обещаниях о доставляемости.

До такого решения Postmaster остаётся внутренним production-инструментом наблюдаемости и управления качеством отправки.
