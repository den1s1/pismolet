# Административная панель доставляемости Mail.ru Postmaster

Статус: PM-3 в работе  
Дата начала: 2026-07-10  
Контур: production  
Связанные документы:

- `docs/mailru_postmaster_api_integration_plan.md`
- `docs/mailru_postmaster_api_sprints.md`
- `docs/mailru_postmaster_sync_architecture.md`
- `docs/mailru_postmaster_api_operations.md`

## 1. Цель

Добавить закрытый административный раздел `/admin/deliverability/mailru`, который показывает накопленные локальные данные Mail.ru Postmaster и не делает внешний API критической зависимостью открытия админки.

Страница предназначена только для администраторов. Данные относятся только к экосистеме Mail.ru и не смешиваются с внутренней статистикой отправки Письмолёта.

## 2. Разделение PM-3 на инкременты

### Инкремент 1 — read-only панель

Реализовано и подтверждено зелёной сборкой и полным набором тестов 2026-07-10:

- отдельная read-модель поверх `MailruPostmasterDbContext`;
- маршрут `/admin/deliverability/mailru` с политикой `AdminOnly`;
- пункт административного меню;
- статус конфигурации и синхронизации;
- последняя попытка, последний успех, последняя обработанная дата и последняя безопасная ошибка;
- активные проблемы SPF, DKIM и DMARC;
- периоды 7, 30 и 90 завершённых московских дней;
- абсолютные значения и рассчитанные по абсолютным значениям доли;
- график объёма/доставки и график нежелательной почты/жалоб;
- предупреждение о низкой выборке при количестве отправленных писем меньше 1000;
- ежедневная таблица метрик;
- SQLite-тесты read-модели и расчётов, тест вставки пункта меню;
- безопасная пустая read-модель для тестового `InMemory`-контура.

Открытие страницы читает только локальную БД и не вызывает OAuth или Mail.ru API.

Инкремент не менял схему БД и не добавлял миграцию.

### Инкремент 2 — ручные операции и журнал запусков

Реализовано в коде, ожидает подтверждения сборки и полного набора тестов:

- ручная команда `Синхронизировать сейчас`;
- защита существующим process-level lock синхронизатора;
- отдельная защита от параллельных ручных запросов;
- ограничение частоты ручного запуска, по умолчанию 60 секунд;
- настройка `MailruPostmaster__ManualSyncCooldownSeconds` с диапазоном 10–3600 секунд;
- понятный результат `успех / ошибка / уже выполняется / ограничение частоты / отключено / не настроено`;
- общий executor для фоновых и ручных запусков;
- постоянный журнал фоновых и ручных запусков;
- additive-миграция `20260710071500_AddMailruPostmasterSyncRunJournal`;
- таблица `mailru_postmaster_sync_runs`;
- отображение последних 20 запусков в админке;
- тесты журнала, executor, ограничения частоты, параллельного ручного запуска, DI и фонового сервиса.

Ручной запуск выполняется только из административного контура и не входит в HTTP-транзакции отправки, оплаты, модерации или пользовательского кабинета.

## 3. Read-модель

Интерфейс:

```csharp
IMailruPostmasterDashboardReader
```

Production-реализация:

```csharp
EfMailruPostmasterDashboardReader
```

Источники:

- `mailru_postmaster_domain_daily_metrics`;
- `mailru_postmaster_trouble_snapshots`;
- `mailru_postmaster_sync_states`;
- `mailru_postmaster_sync_runs`.

Правила:

- домен нормализуется в lowercase без завершающей точки;
- читаются только данные настроенного домена;
- метрики читаются только за выбранный период;
- проблемы фильтруются по `IsActive=true`;
- журнал ограничивается последними 20 запусками;
- EF-запросы выполняются через `AsNoTracking`;
- токены и заголовки авторизации в read-модель не попадают.

## 4. Журнал запусков

Каждая принятая фоновая или ручная попытка создаёт запись со статусом `running`, после чего запись завершается одним из статусов:

- `succeeded`;
- `failed`;
- `cancelled`;
- `disabled`;
- `not_configured`;
- `skipped_already_running`.

Хранятся только безопасные технические поля:

- домен;
- источник запуска `scheduled` или `manual`;
- email администратора для ручного запуска;
- начало, завершение и длительность;
- диапазон дат;
- количество дней метрик и проблем;
- безопасный код ошибки.

Токены, HTTP-заголовки авторизации, сырые ответы API и адреса получателей не сохраняются.

Ошибки создания или завершения записи журнала логируются отдельно и не блокируют саму синхронизацию.

## 5. Ручной запуск и ограничение частоты

Интерфейс:

```csharp
IMailruPostmasterManualSyncService
```

Ручной сервис:

1. Проверяет, что интеграция включена и настроена.
2. Не допускает второй параллельный ручной запрос.
3. Сверяет последний ручной запуск с постоянным журналом и текущим процессом.
4. Применяет cooldown.
5. Передаёт выполнение общему `IMailruPostmasterSyncExecutor`.
6. Использует существующий lock синхронизатора для защиты от пересечения с фоновым запуском.

При совпадении с уже выполняющейся фоновой синхронизацией ручной запуск получает результат `already_running`; параллельный API-вызов не создаётся.

## 6. Периоды и проценты

Доступные периоды:

- 7 дней;
- 30 дней;
- 90 дней.

Период заканчивается вчерашним завершённым календарным днём по Москве. Текущий незавершённый день не включается.

Проценты рассчитываются из суммарных абсолютных значений выбранного периода:

```text
процент = сумма показателя / сумма messages_sent × 100
```

Среднее арифметическое дневных процентов не используется, потому что оно искажает результат при разном объёме по дням.

## 7. Безопасность и отказоустойчивость

- Маршруты GET и POST защищены политикой `AdminOnly`.
- Страница не показывает `refresh_token`, `access_token`, `Authorization` или `Bearer`.
- Ошибка чтения страницы не меняет данные синхронизации и отправки.
- Обычное открытие страницы не выполняет запросы к Mail.ru.
- Ручной внешний запрос выполняется только после явного POST администратора.
- Ошибка журнала не останавливает синхронизацию.
- Ошибка Mail.ru не влияет на SMTP, оплату, модерацию или пользовательский кабинет.
- При `Persistence:Provider=InMemory` используются пустая read-модель, in-memory журнал и отключённая ручная синхронизация.

## 8. Миграция

Миграция:

```text
20260710071500_AddMailruPostmasterSyncRunJournal
```

Изменение additive:

- создаётся только таблица `mailru_postmaster_sync_runs`;
- существующие таблицы PM-2 не изменяются;
- существующие данные не переписываются;
- откат удаляет только новую таблицу журнала.

Production-порядок: резервная копия БД → применение миграции → выкладка приложения → smoke-проверка страницы и ручного запуска.
