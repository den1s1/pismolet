# Архитектура PM-4 — статистика Mail.ru по конкретным рассылкам

Статус: принято к реализации  
Дата фиксации: 2026-07-10  
Контур: production  
Спринт: PM-4  
Ответственное направление: техническое

Связанные документы:

- `docs/mailru_postmaster_api_integration_plan.md`;
- `docs/mailru_postmaster_api_sprints.md`;
- `docs/mailru_postmaster_sync_architecture.md`;
- `docs/mailru_postmaster_admin_architecture.md`;
- `docs/mailru_postmaster_api_operations.md`.

## 1. Цель

PM-4 должен получать статистику Mail.ru Postmaster по конкретной рассылке через параметр `msgtype`, хранить её локально и показывать отдельным блоком в административной карточке рассылки.

Интеграция остаётся контуром наблюдаемости:

- страница администратора читает только локальную БД;
- ошибки OAuth, Mail.ru API или PM-4 storage не блокируют SMTP, оплату, модерацию, кабинет и запуск приложения;
- данные Mail.ru не заменяют внутренние показатели Письмолёта;
- автоматическое влияние на отправку не входит в PM-4.

## 2. Текущее состояние и точка расширения

Уже реализовано:

- SMTP-письма рассылок получают `X-Postmaster-Msgtype`;
- текущее значение строится из идентификатора рассылки, содержит только ASCII-буквы и цифры и ограничено 32 символами;
- `IMailruPostmasterClient.GetStatisticsAsync` и `GetDetailedStatisticsAsync` уже принимают `messageType`;
- доменные метрики, проблемы, состояние синхронизации и журнал запусков хранятся в отдельном `MailruPostmasterDbContext`;
- PM-3 читает только локальную БД и не вызывает Mail.ru API при открытии страницы.

Проблема текущей реализации: правило `msgtype` находится внутри `SmtpEmailProviderAdapter` как закрытый метод. PM-4 не должен копировать это правило. Первым кодовым инкрементом создаётся единый компонент построения `msgtype`, который используют и SMTP-заголовок, и синхронизация статистики рассылок.

## 3. Канонический `msgtype`

Добавить единый компонент, например:

```csharp
public static class MailruPostmasterMessageType
{
    public static string Build(Guid mailingId);
}
```

Каноническое значение:

```text
mailingId.ToString("N")
```

Для `Guid` это ровно 32 символа: цифры и латинские буквы `a-f`, без дефисов.

Правила:

- SMTP и PM-4 обязаны использовать один и тот же компонент;
- нельзя строить `msgtype` из `PublicId`, темы, имени отправителя или адресов получателей;
- результат стабилен для всей жизни рассылки;
- изменение темы, тела, статуса или повторный запуск не меняют `msgtype`;
- в логах допустим `msgtype`, так как он не содержит email-адресов или токенов;
- старые отправленные письма не переписываются.

Текущий закрытый `BuildPostmasterMessageType` в `SmtpEmailProviderAdapter` после переключения всех вызовов удаляется.

## 4. Разделение ответственности

### 4.1. `IMailruPostmasterMailingCandidateReader`

Читает основную БД Письмолёта и возвращает ограниченную выборку рассылок, которым пора обновить статистику.

Для каждой кандидатуры нужны только безопасные технические данные:

- `MailingId`;
- статус рассылки;
- время первой и последней фактической попытки отправки;
- количество фактически обработанных адресатов;
- количество адресатов Mail.ru/VK Mail по внутренним данным, если классификация надёжно доступна;
- текущее состояние PM-4 синхронизации.

Email-адреса получателей в Postmaster storage и логи не передаются.

### 4.2. `IMailruPostmasterMailingStatisticsSynchronizer`

Отвечает за один ограниченный цикл статистики рассылок:

1. Проверить общий и PM-4 feature flag.
2. Выбрать не более `MailingMetricsBatchSize` кандидатур.
3. Для каждой рассылки построить канонический `msgtype`.
4. Рассчитать диапазон завершённых московских дней.
5. Вызвать `GetDetailedStatisticsAsync` с `domain` и `messageType`.
6. Идемпотентно обновить ежедневные метрики рассылки.
7. Обновить отдельное состояние синхронизации этой рассылки.
8. При ошибке изолировать её на уровне одной рассылки.
9. При `429` прекратить текущий PM-4 batch и перенести оставшиеся запросы на следующий запуск.

### 4.3. Существующий доменный synchronizer

PM-4 подключается как отдельная стадия после доменной синхронизации.

Правила изоляции:

- ошибка PM-4 не отменяет уже сохранённые доменные метрики;
- ошибка одной рассылки не прекращает обработку остальных, кроме общего rate limit;
- невозможность записать PM-4 состояние не должна завершать host;
- SMTP никогда не ждёт PM-4.

## 5. Хранилище

Добавить две additive-сущности в существующий `MailruPostmasterDbContext`.

### 5.1. `MailruPostmasterMailingDailyMetricEntity`

Таблица:

```text
mailru_postmaster_mailing_daily_metrics
```

Поля:

- `Id`;
- `MailingId`;
- `MsgType`;
- `Domain`;
- `Date`;
- `MessagesSent`;
- `Delivered`;
- `ProbablySpam`;
- `Spam`;
- `Complaints`;
- `Read`;
- `DeletedRead`;
- `DeletedUnread`;
- `SpamPercent`;
- `ProbablySpamPercent`;
- `Reputation`;
- `Trend`;
- `CollectedAt`;
- `UpdatedAt`.

Уникальный ключ:

```text
Domain + MailingId + Date
```

Дополнительные индексы:

```text
MailingId + Date
MsgType
```

Ежедневное хранение выбрано вместо одной агрегированной строки, потому что оно:

- соответствует уже используемому `GetDetailedStatisticsAsync`;
- допускает идемпотентное уточнение свежих дней;
- сохраняет историю изменения показателей;
- позволяет строить агрегат для любого фактического периода без дублирования окон `DateFrom + DateTo`.

Это уточняет предварительную схему одной агрегированной `MailruPostmasterMailingMetric` из общего плана. Каноническим решением PM-4 является ежедневная таблица.

### 5.2. `MailruPostmasterMailingSyncStateEntity`

Таблица:

```text
mailru_postmaster_mailing_sync_states
```

Ключ:

```text
Domain + MailingId
```

Поля:

- `MailingId`;
- `Domain`;
- `MsgType`;
- `FirstSendAt`;
- `LastSendAt`;
- `LastAttemptAt`;
- `LastSuccessAt`;
- `LastErrorCode`;
- `LastErrorSummary`;
- `ConsecutiveFailures`;
- `LastDateTo`;
- `NextAttemptAt`;
- `LastDataFingerprint`;
- `UnchangedSuccessCount`;
- `HasData`;
- `IsStable`;
- `CompletedAt`;
- `UpdatedAt`.

`LastDataFingerprint` — SHA-256 от нормализованных безопасных числовых метрик, отсортированных по дате. Сырой JSON ответа не хранится.

## 6. Выборка рассылок

Рассылка считается кандидатом, если одновременно выполнено следующее:

- интеграция Mail.ru Postmaster включена;
- PM-4 feature flag включён;
- была хотя бы одна фактическая попытка отправки;
- статус относится к уже начатой отправке: `Sending`, `Sent`, `Failed` или `Paused`;
- отправка началась не раньше настроенной даты появления корректного `X-Postmaster-Msgtype`;
- наступил `NextAttemptAt` либо состояние PM-4 ещё отсутствует;
- статистика не помечена окончательно завершённой.

`Approved` без фактических попыток отправки не синхронизируется.

Сортировка кандидатур:

1. просроченный `NextAttemptAt`;
2. рассылки без первой успешной PM-4 синхронизации;
3. более ранний `LastSuccessAt`;
4. более ранний `FirstSendAt`.

Это обеспечивает справедливую обработку при ограниченном batch и не даёт одной рассылке постоянно вытеснять остальные.

## 7. Конфигурация PM-4

Добавить отдельные настройки с безопасными значениями по умолчанию:

```text
MailruPostmaster__MailingMetricsEnabled=false
MailruPostmaster__MailingMetricsFromDate=2026-07-09
MailruPostmaster__MailingMetricsBatchSize=20
MailruPostmaster__MailingMetricsResyncDays=3
MailruPostmaster__MailingMetricsStableRuns=2
MailruPostmaster__MailingMetricsMaxAgeDays=30
```

Ограничения:

```text
MailingMetricsBatchSize: 1..100
MailingMetricsResyncDays: 1..14
MailingMetricsStableRuns: 1..10
MailingMetricsMaxAgeDays: 7..90
```

`MailingMetricsEnabled=false` отключает только статистику конкретных рассылок. PM-2 и PM-3 продолжают работать.

`MailingMetricsFromDate` запрещает бессмысленный backfill рассылок, отправленных до появления корректного `X-Postmaster-Msgtype`.

## 8. Диапазон статистики

Границы определяются по московским календарным дням.

Для каждой рассылки:

```text
dateFrom = московская дата FirstSendAt
latestCompletedDate = московская дата сегодня - 1 день
dateTo = latestCompletedDate
```

Текущий незавершённый день не запрашивается.

Первый запрос выполняется не раньше появления первого завершённого московского дня после начала отправки.

На повторных запусках допускается запрашивать весь диапазон `dateFrom..dateTo`: объём одной рассылки ограничен, а upsert ежедневных строк идемпотентен. Если реальные объёмы потребуют оптимизации, диапазон можно сузить отдельным изменением без смены схемы хранения.

## 9. Повторные запросы и стабилизация

После успешного ответа:

1. Нормализовать ежедневные метрики и построить безопасный fingerprint.
2. Если fingerprint изменился — сбросить `UnchangedSuccessCount` в `0`.
3. Если fingerprint не изменился — увеличить `UnchangedSuccessCount`.
4. Считать данные стабильными, когда:
   - есть хотя бы одна строка данных;
   - завершилось не менее двух московских дней после `LastSendAt`;
   - fingerprint не изменился `MailingMetricsStableRuns` успешных запусков подряд.

Пока данные не стабильны:

```text
NextAttemptAt = следующий ежедневный цикл
```

После стабилизации:

```text
NextAttemptAt = не раньше чем через 7 дней
```

После достижения `MailingMetricsMaxAgeDays` от `LastSendAt` выполнить финальную попытку и установить `CompletedAt`.

Пустой успешный ответ не считается стабильностью. Состояние `данных пока нет` повторно проверяется до `MailingMetricsMaxAgeDays`, после чего синхронизация завершается без создания фиктивных нулевых метрик.

## 10. Ошибки и rate limit

Для каждой рассылки сохраняются:

- безопасный `ErrorCode`;
- краткое безопасное описание;
- число последовательных ошибок;
- время следующей попытки.

Запрещено сохранять и логировать:

- `refresh_token`;
- `access_token`;
- заголовок `Authorization`;
- сырой JSON;
- email-адреса получателей.

При `429`:

- учитывать `RetryAfter`, если он есть;
- не выполнять оставшиеся запросы PM-4 в текущем цикле;
- не считать доменную синхронизацию неуспешной;
- записать структурированный warning без токенов и сырых ответов.

При `403`, сетевой ошибке, таймауте, `5xx` или невалидном JSON ошибка остаётся локальной для PM-4 и не влияет на отправку.

## 11. Административная карточка рассылки

Добавить локальный reader, например `IMailruPostmasterMailingMetricsReader`.

Карточка рассылки не обращается к Mail.ru API.

Отдельный блок `Mail.ru Postmaster` показывает:

- пояснение «данные только экосистемы Mail.ru»;
- `msgtype`;
- период данных;
- количество адресатов Mail.ru/VK Mail по внутренним данным, если оно рассчитано;
- `messages_sent` Mail.ru;
- доставлено;
- возможно спам;
- спам;
- жалобы;
- прочитано;
- удалено прочитанным и непрочитанным;
- время последнего успешного обновления;
- статус синхронизации.

Состояния UI:

- `ожидает первого завершённого дня`;
- `данных пока нет`;
- `данные обновляются`;
- `данные стабильны`;
- `синхронизация завершена`;
- `последняя попытка завершилась ошибкой`;
- `PM-4 отключён`.

Внутренние показатели Письмолёта и внешние показатели Mail.ru показываются раздельными блоками. Нельзя складывать, усреднять или визуально выдавать их за одну систему измерения.

## 12. Логи и журнал запусков

Добавить структурированные события:

```text
Mail.ru Postmaster mailing statistics batch started.
Mail.ru Postmaster mailing statistics updated.
Mail.ru Postmaster mailing statistics unavailable yet.
Mail.ru Postmaster mailing statistics failed.
Mail.ru Postmaster mailing statistics batch rate limited.
Mail.ru Postmaster mailing statistics batch completed.
```

Безопасные поля:

```text
domain
mailingId
msgtype
dateFrom
dateTo
metricDays
hasData
isStable
processedCount
failedCount
rateLimited
durationMs
```

Адреса получателей и HTTP-body не логируются.

Существующий журнал общих запусков PM-3 не обязан хранить отдельную строку на каждую рассылку. Детальное состояние хранится в `mailru_postmaster_mailing_sync_states`; общий запуск может дополнительно показывать агрегированные счётчики PM-4 отдельным последующим инкрементом.

## 13. Тесты

### 13.1. Единый `msgtype`

- SMTP и PM-4 получают одинаковое значение для одного `MailingId`.
- Значение равно `Guid.ToString("N")`.
- Длина равна 32.
- Допустимы только ASCII-буквы и цифры.

### 13.2. Storage

- Повторный upsert того же `Domain + MailingId + Date` не создаёт дубль.
- Свежие значения обновляют существующую строку.
- Метрики разных рассылок не смешиваются.
- Метрики разных дней сохраняются отдельно.
- Состояние ошибки восстанавливается после успешного запуска.
- Fingerprint и счётчик неизменных запусков обновляются корректно.

### 13.3. Выборка и synchronizer

- Рассылка без фактической отправки не выбирается.
- Рассылка до `MailingMetricsFromDate` не выбирается.
- Первый запрос не выполняется в незавершённый московский день.
- Batch не превышает настройку.
- Используется канонический `msgtype`.
- Пустой ответ сохраняет состояние `данных пока нет` без фиктивной строки.
- Изменившиеся данные сбрасывают счётчик стабильности.
- Неизменные данные переводятся в стабильное состояние.
- `429` прекращает только PM-4 batch.
- Ошибка одной рассылки не блокирует остальные.
- Ошибки PM-4 не выходят в SMTP и host.
- При `MailingMetricsEnabled=false` кандидаты, API и storage не вызываются.

### 13.4. UI

- Блок виден только администратору в карточке рассылки.
- Показано, что данные относятся только к Mail.ru.
- Внутренние и внешние метрики не смешаны.
- Корректно отображаются все состояния без данных, ошибки и стабильной статистики.
- Открытие карточки не вызывает OAuth или Mail.ru API.

## 14. Порядок реализации

### Инкремент 1 — единый `msgtype`

1. Добавить `MailruPostmasterMessageType`.
2. Перевести SMTP-заголовок на новый компонент.
3. Удалить закрытую копию правила из `SmtpEmailProviderAdapter`.
4. Обновить тесты без reflection к закрытому методу.
5. Подтвердить неизменность фактического значения заголовка.

### Инкремент 2 — storage

1. Добавить ежедневные метрики и состояние PM-4.
2. Добавить конфигурацию и feature flag.
3. Создать additive-миграцию и snapshot.
4. Реализовать идемпотентный storage.
5. Добавить SQLite-тесты.

### Инкремент 3 — выборка и синхронизация

1. Реализовать candidate reader.
2. Реализовать ограниченный batch.
3. Добавить повторные запросы, fingerprint и стабилизацию.
4. Изолировать ошибки и `429`.
5. Подключить к существующему ежедневному и ручному циклу.
6. Добавить интеграционные тесты без реального Mail.ru API.

### Инкремент 4 — административная карточка

1. Добавить локальный reader.
2. Добавить отдельный блок Mail.ru Postmaster.
3. Добавить состояния без данных, ошибки и стабильности.
4. Добавить UI-тесты и проверку отсутствия внешнего API при открытии страницы.

### Инкремент 5 — production rollout

1. Создать backup БД.
2. Применить additive-миграцию.
3. Развернуть код с `MailingMetricsEnabled=false`.
4. Проверить PM-2, PM-3, SMTP, health и логи.
5. Включить PM-4.
6. Выполнить ограниченную ручную синхронизацию.
7. Проверить реальный `msgtype` и локальные строки БД.
8. На следующий завершённый день сверить показатели с интерфейсом Mail.ru Postmaster.

## 15. Границы PM-4

Не входят:

- автоматическая остановка, замедление или блокировка отправки;
- изменение модерации на основании статистики Mail.ru;
- показ данных Mail.ru клиенту;
- получение адресов пожаловавшихся пользователей;
- хранение сырых ответов API;
- распределённый lock для multi-instance deployment;
- исторический backfill рассылок до даты корректного `X-Postmaster-Msgtype`;
- PM-5 предупреждения и PM-6 автоматическое управление доставляемостью.

## 16. Критерий завершения PM-4

PM-4 считается внедрённым, когда:

- SMTP и synchronizer используют единый `msgtype`;
- additive-миграция применена в production;
- ограниченный batch получает и идемпотентно обновляет статистику по реальному `msgtype`;
- повторные запросы и стабилизация работают;
- административная карточка читает только локальную БД и раздельно показывает внутренние и Mail.ru показатели;
- пустые данные и ошибки отображаются безопасно;
- полный набор тестов зелёный;
- production smoke подтверждает независимость SMTP и отсутствие секретов в логах.
