# Production runbook Письмолёта

Статус: действующая техническая инструкция  
Дата фиксации: 2026-07-11  
Ответственное направление: техническое

## 1. Постоянные параметры production

- checkout репозитория: `/opt/pismolet`;
- systemd-сервис: `pismolet.service`;
- публичное приложение: `https://app.pismolet.ru`;
- health endpoint: `https://app.pismolet.ru/health`;
- имя основной PostgreSQL-базы приложения: `pismolet`;
- локальное подключение для административных проверок: `sudo -u postgres psql -d pismolet`;
- база `postgres` является служебной базой PostgreSQL и не должна использоваться вместо основной базы приложения;
- файл `/etc/pismolet/pismolet.env` является `EnvironmentFile` для systemd; его нельзя выполнять через `source`.

Не выводить в терминал, журналы, чат или документацию секреты, токены, полные строки подключения и значения переменных окружения.

## 2. Обязательный порядок выкладки

Каждая операция выполняется отдельно, с проверкой результата перед следующим шагом.

1. Удалить сгенерированные `bin/` и `obj/` из checkout.
2. Проверить чистоту рабочего дерева.
3. Получить актуальный `Development` через fast-forward pull.
4. Выполнить `build-pismolet`.
5. Выполнить `run-tests-pismolet`.
6. До deploy определить, меняется ли схема БД:
   - проверить новые EF-миграции;
   - выписать ожидаемые таблицы, колонки, индексы и ограничения;
   - подготовить запрос проверки фактической схемы production.
7. Выполнить `deploy-pismolet`.
8. Сразу после deploy проверить применение изменений схемы БД.
9. Проверить `systemctl is-active pismolet.service`.
10. Проверить health endpoint.
11. Проверить журнал сервиса на `fail:`, необработанные исключения, HTTP 500 и ошибки PostgreSQL.
12. Выполнить функциональный smoke изменённого пользовательского сценария.

Успешный health сам по себе не подтверждает успешную выкладку: endpoint может отвечать `200`, даже если пользовательские страницы падают из-за несоответствия схемы БД.

## 3. Проверка схемы PostgreSQL

Основная база production всегда указывается явно:

```bash
sudo -u postgres psql -d pismolet
```

Для проверки конкретной колонки использовать `information_schema.columns`, не выводя содержимое пользовательских таблиц.

Пример для `mailings."RecipientReason"`:

```bash
sudo -u postgres psql -d pismolet -Atqc "SELECT column_name, data_type, character_maximum_length, is_nullable FROM information_schema.columns WHERE table_schema='public' AND table_name='mailings' AND column_name='RecipientReason';"
```

Ожидаемый результат для PM-1A:

```text
RecipientReason|character varying|1000|YES
```

Наличие файла EF-миграции в репозитории не считается доказательством того, что миграция применена к production-БД.

## 4. Инцидент «код ожидает колонку, а БД её не содержит»

Характерный признак в журнале PostgreSQL/Npgsql:

```text
SqlState: 42703
column ... does not exist
```

Порядок действий:

1. Найти точное имя отсутствующей колонки и затронутую таблицу в журнале.
2. Сверить тип, длину, nullable-режим и имя колонки с EF-моделью и миграцией в `Development`.
3. Для срочного восстановления применять только минимальное идемпотентное DDL-изменение, соответствующее уже проверенной миграции.
4. Повторно проверить фактическую схему через `information_schema`.
5. Проверить активность сервиса, health и журнал после исправления.
6. Повторить пользовательский сценарий, который давал HTTP 500.
7. Зафиксировать инцидент и причину в технической документации.

Для PM-1A аварийное восстановление production было выполнено командой:

```bash
sudo -u postgres psql -d pismolet -c 'ALTER TABLE mailings ADD COLUMN IF NOT EXISTS "RecipientReason" character varying(1000);'
```

Эта команда допустима только для данного уже проверенного изменения. Для других изменений нельзя копировать её без сверки с актуальной моделью и миграцией.

## 5. Критерии завершённой выкладки

Выкладка считается подтверждённой только когда одновременно выполнены все условия:

- сборка успешна;
- полный набор автоматических тестов успешен;
- production использует нужный commit;
- схема production-БД соответствует коду;
- `pismolet.service` активен;
- health возвращает успешный ответ;
- в журнале нет новых критических ошибок;
- изменённый пользовательский сценарий прошёл ручной smoke.

До выполнения функционального smoke нельзя считать изменение полностью подтверждённым в production.
