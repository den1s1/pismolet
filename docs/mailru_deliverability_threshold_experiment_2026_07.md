## 1. Цель

Проверить гипотезу, что Mail.ru применяет к новому или низкорепутационному отправителю динамический объёмный или репутационный бюджет, после исчерпания которого письма начинают массово классифицироваться как «Возможно спам», а после паузы или пересчёта состояние восстанавливается.

Эксперимент не должен специально провоцировать большой объём после появления первого отрицательного сигнала.

## 2. Основной принцип

Продолжать отправку одинакового письма отдельными небольшими рассылками. После каждой рассылки дождаться появления её результата в Mail.ru Postmaster. При первой рассылке с заметным ухудшением остановить дальнейшую отправку и сохранить данные.

Ключевое правило:

> каждая пачка должна быть отдельной рассылкой с отдельным `MailingId` и отдельным `X-Postmaster-Msgtype`.

Если разделить адресатов внутри одной рассылки, Mail.ru Postmaster API не позволит надёжно отделить одну пачку от другой, потому что весь объём будет иметь один `msgtype`.

## 3. Размер пачки

Предложенный рабочий размер:

- 20 реальных адресов Mail.ru;
- при необходимости 1 собственный технический адрес как положительный контроль.

Если используется схема `20 + 1`, в расчётах считать фактический объём равным 21 письму Mail.ru, а не 20.

Для более чистой арифметики можно использовать 19 реальных адресов и 1 технический, то есть 20 писем Mail.ru на пачку. Выбор должен быть зафиксирован до начала серии и не меняться внутри неё.

## 4. Условия, которые нельзя менять внутри серии

Для всех пачек одной серии сохранить одинаковыми:

- тему;
- имя отправителя;
- исходный шаблон;
- ссылки;
- отсутствие или наличие вложений;
- режим click-tracking: выключен;
- HTML/text режим;
- причину получения письма;
- служебный footer;
- SMTP, DNS, Postfix, OpenDKIM и отправляющий IP;
- минимальный интервал отправки приложения;
- размер пачки;
- число собственных технических адресов.

Допустимые изменения по определению:

- `MailingId`;
- `X-Postmaster-Msgtype`;
- `Message-ID`;
- персональный токен отписки;
- токен пикселя открытия;
- адрес получателя.

## 5. Выбор получателей

Чтобы не спутать порог с качеством конкретной группы:

1. Использовать одну однородную базу активных и ожидающих письмо адресатов.
2. До начала серии случайно перемешать список.
3. Разделить список на пачки заранее, а не выбирать следующую группу после просмотра результата.
4. Не помещать все самые активные адреса в первые пачки и все старые адреса в последние.
5. Собственные технические адреса учитывать отдельно от реальных.
6. Зафиксировать пересечение с получателями 2026-07-12 и 2026-07-13.

## 6. Порядок отправки

Для каждой пачки:

1. Создать отдельную рассылку.
2. Зафиксировать до старта:
   - `MailingId`;
   - ожидаемый `msgtype`;
   - время старта;
   - число реальных адресов;
   - число технических адресов;
   - накопленный объём Mail.ru за предыдущие 1, 3, 6, 12, 24 и 48 часов.
3. Отправить пачку.
4. Зафиксировать время последнего SMTP-принятия.
5. Не отправлять следующую пачку, пока Postmaster не отразит ожидаемое увеличение счётчика и результат текущей пачки либо пока не станет ясно, что обновление отложено.
6. После появления данных записать:
   - писем;
   - доставлено;
   - «Возможно спам»;
   - «Точно спам»;
   - жалобы;
   - прочитано;
   - удалено прочитанным;
   - удалено непрочитанным.
7. Только при нормальном результате перейти к следующей пачке.

## 7. Критерий остановки

Немедленно прекратить дальнейшие пачки, если выполняется хотя бы одно условие:

- `probably_spam > 0` в пачке после серии полностью успешных пачек;
- доля «Возможно спам» составляет 10% или более;
- большинство реальных адресов пачки попало в «Возможно спам»;
- появились жалобы;
- появились массовые 4xx/5xx, hard bounce или проблемы SPF/DKIM/DMARC;
- данные ЛК и API расходятся так, что результат нельзя надёжно атрибутировать.

Первое единичное письмо «Возможно спам» не доказывает порог, но является достаточным основанием остановиться и не ухудшать репутационный сигнал.

## 8. Что даст первая плохая пачка

Пусть до неё успешно прошло `L` писем Mail.ru, а размер новой пачки равен `B`.

Тогда наблюдаемый переход локализован только в диапазоне:

`L < предполагаемая граница или состояние <= L + B`.

Это не доказывает фиксированный лимит, потому что одновременно могут действовать:

- скользящее окно;
- пересчёт репутации;
- профиль получателей;
- временное policy-состояние;
- задержка обновления Postmaster.

Не следует в тот же день уменьшать пачку и продолжать «дожимать» точное число после появления массового спама.

## 9. Роль Mail.ru Postmaster API

### 9.1. Что API даст

Текущая интеграция поддерживает:

- доменную статистику;
- детальную ежедневную статистику;
- фильтрацию по `msgtype` конкретной рассылки;
- показатели `MessagesSent`, `Delivered`, `ProbablySpam`, `Spam`, `Complaints`, `Read`, `DeletedRead`, `DeletedUnread` и производные проценты;
- хранение истории в локальной БД;
- повторную синхронизацию свежих дней;
- отдельную административную карточку Mail.ru Postmaster для рассылки.

Это позволит:

1. Надёжно разделить результаты отдельных пачек при условии отдельного `MailingId/msgtype`.
2. Определить первую полностью или частично плохую пачку.
3. Посчитать накопленный объём перед ней по внутренним timestamps Письмолёта.
4. Сопоставить доменный дневной агрегат с суммой отдельных рассылок.
5. Обнаружить необъяснённые письма, как расхождение 57 против 69 за 2026-07-12.
6. Повторно синхронизировать данные, если Mail.ru уточнил статистику позже.

### 9.2. Чего API не даст

API не раскрывает:

- внутренний антиспам-score;
- конкретный reason code для «Возможно спам»;
- опубликованное значение динамического лимита;
- точный момент внутри пачки, после которого переключилась классификация;
- классификацию каждого отдельного адресата;
- сведения о спам-ловушке;
- точную причину восстановления на следующий день;
- рекомендации по исправлению конкретного внутреннего сигнала.

Поэтому API позволяет локализовать наблюдаемый переход по пачкам, но не доказывает внутренний механизм Mail.ru.

## 10. Ограничения текущей реализации интеграции

Текущий production-контур имеет ограничения:

- доменная синхронизация не запрашивает текущий незавершённый день по Москве;
- статистика конкретной рассылки запрашивается не ранее следующего дня;
- фоновая синхронизация запускается один раз в сутки;
- PM-4 временно работает с `MailingMetricsBatchSize=1`;
- административная карточка читает локальную БД и не обращается к API при открытии.

Следствие:

> текущая интеграция пригодна для точного анализа после появления данных, но не является достаточным каналом для остановки серии в реальном времени.

Для оперативного решения «отправлять следующую пачку или остановиться» в текущем эксперименте основным источником остаётся ЛК Mail.ru Postmaster. Следующую пачку нельзя отправлять, пока результат предыдущей не стал наблюдаемым.

## 11. Технические улучшения перед расширением эксперимента

После первого контролируемого дня отдельно рассмотреть:

1. Проверить, появились ли фактические метрики PM-4 по новым рассылкам.
2. После подтверждения стабильности PM-4 увеличить `MailingMetricsBatchSize` с 1 до значения, покрывающего все экспериментальные пачки, например 20.
3. Добавить административный отчёт эксперимента, объединяющий:
   - внутренние времена отправки;
   - объём за скользящие окна;
   - `MailingId/msgtype`;
   - внешние метрики Postmaster.
4. Не добавлять автоматическую остановку рассылок по одному значению Postmaster до накопления нескольких повторяемых наблюдений.
5. Отдельно проверить, возвращает ли официальный API полезные данные по текущему незавершённому дню; не менять рабочую синхронизацию до подтверждения поведения.

## 13. Итоговое решение

План отправлять отдельными пачками и остановиться при первом заметном ухудшении принят как контролируемое наблюдение при условиях:

- отдельная рассылка и отдельный `msgtype` на каждую пачку;
- неизменность письма и инфраструктуры;
- однородная случайно распределённая база;
- ожидание результата предыдущей пачки перед следующей;
- остановка при первом отрицательном сигнале;
- использование ЛК Postmaster для оперативного контроля;
- использование API и локальной БД для последующего точного анализа по рассылкам.
