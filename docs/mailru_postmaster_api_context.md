## 2. Подтверждённые свойства API

Официальная документация подтверждает:

- статистика Postmaster относится к домену из тега `d=` DKIM-подписи; значение заголовка `From` для этой привязки не используется;
- API работает через OAuth 2.0;
- `refresh_token` является долговременным и используется для получения краткоживущего `access_token`;
- время жизни `access_token` — 1 час;
- `access_token` передаётся в заголовке `Bearer`;
- `/ext-api/reg-list/` возвращает подтверждённые домены;
- `/ext-api/troubles-list/` возвращает проблемы SPF, DKIM и DMARC;
- `/ext-api/stat-list/` возвращает агрегированную статистику за период;
- `/ext-api/stat-list-detailed/` возвращает статистику с разбивкой по дням;
- статистику можно фильтровать по `domain` и `msgtype`;
- `msgtype` берётся из заголовков `X-Mailru-Msgtype` или `X-Postmaster-Msgtype`;
- `msgtype` используется только совместно с доменом;
- период начинается с обязательного `date_from`, а дата не должна быть старше одного года;
- API возвращает показатели `messages_sent`, `delivered`, `probably_spam`, `spam`, `complaints`, `read`, `deleted_read`, `deleted_unread`, процентные показатели, а в детальной статистике также `reputation` и `trend`;
- лимит составляет 10 обращений в минуту для каждой группы методов по каждому домену с одного аккаунта;
- `403` требует обновления `access_token` через `refresh_token`;
- `429` означает превышение лимита и содержит указание, через сколько секунд запрос может быть повторён.

## 3. Зачем Письмолёту эта интеграция

Письмолёт уже отправляет письма. Интеграция Postmaster не нужна для самой SMTP-отправки и не должна становиться её обязательной зависимостью.

Цель интеграции — получить внутренний production-инструмент наблюдаемости за тем, как экосистема Mail.ru принимает и классифицирует письма домена `pismolet.ru`.

Практическая причина запуска работ: при росте объёма был замечен значимый показатель категории «Возможно спам». Ручной просмотр кабинета Postmaster не даёт надёжного ежедневного контроля, исторических сравнений внутри Письмолёта и операционного журнала.

Интеграция должна позволять:

1. Автоматически получать данные Mail.ru Postmaster.
2. Хранить собственную ежедневную историю.
3. Показывать динамику за 7, 30 и 90 дней.
4. Видеть абсолютные значения рядом с процентами.
5. Обнаруживать проблемы SPF, DKIM и DMARC.
6. Видеть рост `probably_spam`, `spam` и жалоб.
7. Позднее получать статистику по отдельным рассылкам через `msgtype`.
8. Создать основу для предупреждений и осторожного управления доставляемостью после накопления истории и отдельного утверждения правил.

## 4. Архитектурная граница

Postmaster является контуром наблюдаемости, а не критической зависимостью отправки.

Обязательные правила:

- недоступность Mail.ru API не останавливает отправку писем;
- ошибки OAuth не блокируют кабинет, оплату, модерацию и SMTP;
- открытие административной страницы читает локальную БД, а не вызывает Mail.ru API;
- синхронизация выполняется вне транзакций отправки;
- ошибки API и Postmaster storage изолируются от application host и SMTP;
- автоматическая остановка рассылок или блокировка клиентов только по одному показателю Postmaster не допускается;
- автоматическое влияние на скорость отправки возможно только отдельным решением после периода наблюдения, с журналом причин, аварийным отключением и ручным контролем.

## 5. Реализованные этапы

### PRE — инфраструктура домена

В production подтверждены:

- домен `pismolet.ru`;
- SPF;
- DKIM;
- DMARC;
- FBL;
- корректный `X-Postmaster-Msgtype`.

### PM-1 — OAuth и API-клиент

В production внедрены:

- безопасная конфигурация;
- OAuth и кеш `access_token` в памяти;
- типизированный API-клиент;
- обработка `403`, `429`, `5xx`, таймаутов, сетевых ошибок и невалидного JSON;
- диагностика подтверждённого домена и проблем SPF/DKIM/DMARC;
- служебные заголовки массового письма.

### PM-2 — локальная история и ежедневная синхронизация

В production внедрены:

- отдельный `MailruPostmasterDbContext`;
- ежедневные доменные метрики;
- снимки проблем;
- состояние синхронизации;
- первичный backfill;
- ежедневная синхронизация завершённых московских дней;
- идемпотентный upsert и защита от дублей;
- изоляция ошибок API и БД Postmaster от отправки.

Production smoke PM-2 подтвердил:

- 20 дней фактических метрик;
- отсутствие дублей;
- успешный повторный свежий диапазон;
- рабочий `/health`;
- отсутствие warning/error и утечек токенов;
- успешную доставку обычного тестового письма.

### PM-3 — административная панель доменной доставляемости

Код реализован и автоматические проверки зелёные.

PM-3 добавляет:

- `/admin/deliverability/mailru`;
- пункт административного меню;
- локальные метрики и графики за 7, 30 и 90 дней;
- абсолютные значения рядом с процентами;
- предупреждение о малой выборке;
- проблемы SPF/DKIM/DMARC;
- ручную синхронизацию;
- cooldown ручного запуска;
- постоянный журнал scheduled/manual запусков.
