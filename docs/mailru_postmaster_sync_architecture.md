# Архитектура фоновой синхронизации Mail.ru Postmaster

Статус: принято к реализации  
Дата фиксации: 2026-07-09  
Контур: production  
Спринт: PM-2  
Связанные документы:

- `docs/mailru_postmaster_api_integration_plan.md`
- `docs/mailru_postmaster_api_sprints.md`
- `docs/mailru_postmaster_api_operations.md`

## 1. Назначение

Документ уточняет реализацию `MailruPostmasterSyncHostedService` в рамках PM-2. Общие продуктовые и эксплуатационные требования остаются в `docs/mailru_postmaster_api_integration_plan.md`.

Фоновая синхронизация должна:

- ежедневно получать доменные метрики и проблемы Mail.ru Postmaster;
- выполнять первичный backfill;
- повторно синхронизировать свежие дни, поскольку статистика может уточняться позднее;
- догружать пропущенные дни после простоя или временных ошибок;
- сохранять данные идемпотентно;
- не становиться критической зависимостью отправки писем или запуска приложения.

## 2. Разделение ответственности

### `MailruPostmasterSyncHostedService`

Отвечает только за жизненный цикл фонового процесса:

- проверяет, включена ли интеграция;
- вычисляет время следующего запуска по московскому времени;
- запускает одну синхронизацию через отдельный orchestrator;
- передаёт `CancellationToken` остановки приложения;
- корректно завершает ожидание и текущий запуск при остановке host;
- не пробрасывает ошибки API или БД наружу в host.

### `IMailruPostmasterSynchronizer`

Отвечает за один полный цикл API → storage:

1. Проверить конфигурацию интеграции.
2. Не допустить параллельный запуск.
3. Создать DI scope и получить `IMailruPostmasterStorage`.
4. Прочитать persistent sync state.
5. Зафиксировать попытку синхронизации.
6. Получить список зарегистрированных доменов.
7. Проверить наличие настроенного домена.
8. Получить список проблем домена.
9. Рассчитать диапазон ежедневной статистики.
10. Получить детальную статистику.
11. Идемпотентно обновить метрики и проблемы.
12. Зафиксировать успешное состояние либо безопасно обработать ошибку.

Разделение необходимо, чтобы алгоритм одного запуска можно было тестировать без запуска ASP.NET-host и повторно использовать в будущем для ручной синхронизации в административной панели.

## 3. Конфигурация

Используются параметры:

```text
MailruPostmaster__Enabled=true
MailruPostmaster__Domain=pismolet.ru
MailruPostmaster__SyncHourMoscow=6
MailruPostmaster__BackfillDays=30
MailruPostmaster__ResyncRecentDays=3
```

Значения по умолчанию:

```text
SyncHourMoscow=6
BackfillDays=30
ResyncRecentDays=3
```

Допустимые пределы:

```text
SyncHourMoscow: 0..23
BackfillDays: 1..365
ResyncRecentDays: 1..30
```

При `MailruPostmaster__Enabled=false` фоновый процесс не должен обращаться ни к Mail.ru API, ни к Postmaster storage.

## 4. Московское календарное время

Расписание и границы календарных дней определяются в часовом поясе Москвы.

Основной идентификатор часового пояса:

```text
Europe/Moscow
```

Допустим fallback для Windows:

```text
Russian Standard Time
```

Каждый следующий запуск вычисляется заново относительно московской календарной даты и `SyncHourMoscow`. Не используется бесконечный интервал ровно в 24 часа, чтобы время запуска не смещалось после перезапусков и задержек.

## 5. Завершённый день

Синхронизация доменной статистики выполняется только до вчерашнего дня включительно по московскому времени.

```text
latestCompletedDate = московская дата сегодня - 1 день
```

Текущий календарный день не сохраняется как завершённый, поскольку его статистика неполная и может существенно измениться.

## 6. Первичный backfill

Если sync state отсутствует либо `LastDomainDate` не заполнен:

```text
dateTo = latestCompletedDate
dateFrom = dateTo - (BackfillDays - 1)
```

При `BackfillDays=30` диапазон содержит ровно 30 календарных дней включительно.

Повторный запуск первого диапазона не должен создавать дубли. Идемпотентность обеспечивается существующим уникальным ключом `Domain + Date` и upsert в `IMailruPostmasterStorage`.

## 7. Повторная синхронизация и восстановление пропусков

Если `LastDomainDate` заполнен:

```text
nextUnsynchronizedDate = LastDomainDate + 1 день
recentRangeStart = latestCompletedDate - (ResyncRecentDays - 1)
dateFrom = Min(nextUnsynchronizedDate, recentRangeStart)
dateTo = latestCompletedDate
```

Алгоритм одновременно:

- повторно обновляет последние `ResyncRecentDays`;
- догружает дни, пропущенные после длительного простоя;
- не теряет диапазон после временной ошибки;
- не создаёт дубли при повторном выполнении.

После успешного запроса в `LastDomainDate` записывается `dateTo`, а не максимальная дата из ответа API. Это предотвращает бесконечное повторение дней, в которые не было отправок и которые поэтому могут отсутствовать в ответе.

Если рассчитанный `dateFrom` позже `dateTo`, запрос статистики не выполняется, но проблемы домена и состояние синхронизации могут быть обновлены.

## 8. Защита от параллельного запуска

В текущем single-instance production используется process-level блокировка внутри singleton-orchestrator, например `SemaphoreSlim` с немедленной попыткой захвата.

Если предыдущий запуск ещё выполняется:

- новый запуск пропускается;
- создаётся структурированная информационная запись в журнале;
- исключение не выбрасывается.

При переходе к нескольким одновременно работающим экземплярам приложения потребуется отдельное решение с распределённой блокировкой, например PostgreSQL advisory lock. Это не входит в текущий инкремент PM-2.

## 9. Ошибки API и storage

Mail.ru Postmaster не является критической зависимостью пользовательского сценария.

Ошибки API:

- фиксируются структурированным логом;
- по возможности записываются через `MarkFailureAsync`;
- завершают только текущий цикл синхронизации;
- не влияют на отправку писем, оплату, модерацию, кабинет и запуск host.

Ошибки Postmaster storage:

- фиксируются в обычном application log;
- не должны приводить к повторной бесконечной записи ошибки в ту же недоступную БД;
- завершают только текущий цикл;
- не пробрасываются наружу из hosted service.

Ошибка самого `MarkFailureAsync` не должна маскировать первоначальную ошибку API и не должна завершать host.

`OperationCanceledException`, вызванная токеном остановки приложения, рассматривается как штатная остановка и не записывается как ошибка интеграции.

## 10. Структурированные логи

Минимальный набор событий:

### Начало

```text
Mail.ru Postmaster synchronization started.
domain={Domain}
dateFrom={DateFrom}
dateTo={DateTo}
isBackfill={IsBackfill}
```

### Успех

```text
Mail.ru Postmaster synchronization completed.
domain={Domain}
dateFrom={DateFrom}
dateTo={DateTo}
metricDays={MetricDays}
troubleCount={TroubleCount}
durationMs={DurationMs}
```

### Ошибка

```text
Mail.ru Postmaster synchronization failed.
domain={Domain}
stage={Stage}
errorCode={ErrorCode}
dateFrom={DateFrom}
dateTo={DateTo}
```

### Пропуск параллельного запуска

```text
Mail.ru Postmaster synchronization skipped because another run is active.
domain={Domain}
```

Запрещено логировать:

- `refresh_token`;
- `access_token`;
- заголовок `Authorization`;
- полный сырой ответ OAuth или Postmaster API.

## 11. Регистрация зависимостей

Регистрация синхронизации выполняется через существующие extension-методы DI инфраструктуры.

`Program.cs` изменять не требуется, если синхронизацию можно подключить внутри уже вызываемого Postmaster extension-метода.

Точная строка чтения `InboundReplies:MaxFilesPerPoll` в `Program.cs` не изменяется.

## 12. Тесты текущего инкремента

Обязательные автоматические сценарии:

1. Первый запуск запрашивает backfill за `BackfillDays`.
2. Повторный запуск обновляет существующие строки без дублей.
3. Повторный запуск запрашивает последние `ResyncRecentDays`.
4. После пропущенных дней диапазон включает накопившийся разрыв.
5. `LastDomainDate` обновляется концом запрошенного диапазона.
6. Ошибка API фиксирует состояние ошибки.
7. Следующий запуск восстанавливается после ошибки.
8. Ошибка Postmaster storage не выходит в host.
9. Параллельный запуск пропускается.
10. `CancellationToken` корректно останавливает ожидание и текущий запуск.
11. При `Enabled=false` API и storage не вызываются.
12. Реальные запросы к Mail.ru в unit- и integration-тестах не выполняются.

## 13. Границы инкремента

В текущий инкремент не входят:

- статистика по отдельным рассылкам и `msgtype` — PM-4;
- административная страница и ручной запуск — PM-3;
- пороговые предупреждения — PM-5;
- распределённая блокировка для нескольких экземпляров приложения;
- изменение SMTP-отправки;
- новая миграция БД, если существующей схемы sync state достаточно.
